# StudyPilot 面试讲解提纲

## 30 秒介绍

StudyPilot 解决的是“课程 PDF 很长、普通聊天机器人回答无法核查”的问题。学生上传自己的资料后，可以得到带页码引用的问答、基于原文生成的测验和错题分析。项目重点不只是接入模型，而是完整处理了用户隔离、失败恢复、结构化输出、可重复评测和端到端交付。

## 为什么用 pgvector？

MVP 的用户、课程、文档、对话、测验本来就是强关系数据。把向量与文档分块放在同一个 PostgreSQL 中，可以用外键和事务保持一致，并在查询中直接按 `course_id` 与文档状态过滤，减少一套向量数据库的部署和同步成本。规模增大后再评估 HNSW 索引、分区或独立检索服务。

## 引用是怎么工作的？

检索结果被编号为 `S1...S5`。模型只能在回答里输出这些编号，服务端用正则再次校验：不存在的编号会删除；非拒答回答若没有任何有效编号就返回错误，不把无依据答案展示给用户。保存的引用包含文档 ID、文件名、实际 PDF 页码、片段和距离，前端将 `[S1]` 转成可点击引用。

## 如何降低幻觉？

限制回答范围、检索距离阈值、最多五个来源、明确的资料不足拒答、引用白名单、无引用失败、提示注入隔离，以及离线评测共同降低风险。它们不能数学上消灭幻觉，因此界面仍明确定位为学习辅助，而不是权威答案。

## 为什么没用 LangChain？

流程只有解析、分块、向量化、检索、提示构造和结构化校验几个稳定步骤。直接使用小接口和普通 Python 让异常映射、事务边界、Token 统计和测试替身更透明，也减少版本耦合。若未来出现复杂工具编排或多步代理，再基于实际复杂度引入框架。

## 怎样防止跨用户访问？

JWT 只提供 `user_id`。课程查询必须同时匹配 `course.id` 与 `owner_id`；文档、对话、测验和分析入口都先验证所属课程或直接带用户过滤。对象键是不可猜 UUID，Supabase bucket 私有，前端永远拿不到 service-role key。测试覆盖“另一个用户得到 404”而不是泄漏资源是否存在。

## 模型返回非法 JSON 怎么办？

先要求供应商使用 JSON Schema，再用 Pydantic做第二次验证，包括题型、题数、四个唯一选项、标准答案必须在选项内、来源文档和页码必须存在于上下文。第一次失败时把精简校验错误发给模型修复；第二次仍失败则返回稳定的 502/503 错误，不保存半成品。

## 上生产规模后会改什么？

将 PDF 处理移到持久队列与独立 worker，增加任务租约、幂等键和死信队列；对象存储使用签名 URL；数据库加入连接池、向量索引、只读副本和分区；配套速率限制、审计日志、指标告警、内容安全策略与数据删除流程。模型层增加熔断、供应商回退、成本预算与在线质量采样。

## 可主动展示的工程点

- 生产环境硬拒绝假 AI，CI 不使用真实密钥或产生模型费用。
- 文档状态机保存可解释失败原因，重启时会恢复超时任务。
- RAG 评测集固定文档哈希、许可、20 个问题和指标口径。
